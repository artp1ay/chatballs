# Руководство по настройке режимов маршрутизации каналов и Rules Engine

**Версия документации:** 1.0  
**Статус:** Действующая документация  
**Связанные проектные документы:** [PRD (HOM-10)](/HOM/issues/HOM-10), [Техническая архитектура (HOM-11)](/HOM/issues/HOM-11), [Тестовый план (HOM-9)](/HOM/issues/HOM-9)  
**Область применения:** Платформа омниканальной клиентской поддержки Chatballs

---

## 1. Введение и концепция гибридной поддержки

Исторически платформа Chatballs функционировала в парадигме **«AI-First по умолчанию»**: все входящие обращения из каналов коммуникации (Telegram, VK, виджет на сайте, Email) безусловно принимались виртуальным AI-агентом, если он был настроен и активен на канале.

С выходом обновленной системы гибкой маршрутизации платформа трансформирована в **гибридную систему клиентской поддержки (Human-in-the-Loop / AI-assisted)**. Бизнес получает полный и прозрачный контроль над тем, **где, когда и при каких условиях** к диалогам подключается искусственный интеллект, а когда обслуживание должно производиться исключительно живыми операторами.

### Ключевые возможности:
- **Выбор стратегии на уровне канала:** мгновенное переключение канала связи в режим классического Helpdesk (только люди), гибридный режим (по бизнес-правилам) или классический AI-First.
- **Движок бизнес-правил (Rules Engine):** гибкая оценка контекста входящего обращения (время суток, рабочий график компании, метки клиента, наличие подтвержденного телефона, стоп-слова, темы претензий, регулярные выражения).
- **Бесшовный переход и перехват:** оператор может перехватить диалог у ИИ в один клик или отправкой первой фразы в чат без технических задержек и дублирования ответов клиенту.
- **Гарантированная защита от потерь сообщений:** многоуровневый Fallback исключает потерю сообщений при технических сбоях провайдеров больших языковых моделей (LLM) или отсутствии совпадений в правилах.

## 2. Руководство администратора и супервайзера

Данный раздел предназначен для руководителей службы поддержки, супервайзеров и системных администраторов, настраивающих каналы связи и политики обслуживания клиентов.

### 2.1. Режимы работы канала связи (`Routing Mode`)

Каждый подключенный канал связи (`Channel`) обладает собственным независимым параметром **«Режим обработки обращений» (Routing Mode)**. Настройка доступна в панели управления:  
`Панель управления` → `Каналы связи` → Выберите канал → вкладка `Маршрутизация`.

```
                    ┌──────────────────────────────────────────────┐
                    │   Входящее сообщение клиента в канал связи   │
                    └──────────────────────┬───────────────────────┘
                                           │
                    ┌──────────────────────▼───────────────────────┐
                    │       Проверка режима маршрутизации канала   │
                    └──────┬───────────────┬────────────────┬──────┘
                           │               │                │
            ┌──────────────┘               │                └──────────────┐
            ▼                              ▼                               ▼
 ┌─────────────────────┐        ┌─────────────────────┐        ┌─────────────────────┐
 │ 1. Только операторы │        │ 2. По правилам      │        │ 3. ИИ-агент         │
 │    (HUMAN_ONLY)     │        │    (RULE_BASED)     │        │    (AI_FIRST)       │
 └──────────┬──────────┘        └──────────┬──────────┘        └──────────┬──────────┘
            │                              │                              │
            ▼                              ▼                              ▼
  Диалог создается в             Rules Engine оценивает          ИИ отвечает первым.
  очереди операторов.            условия (график, клиент,        При сбое или эскалации
  ИИ полностью молчит.           слова) и выбирает маршрут.      — передача операторам.
```

#### 1. Только операторы (`HUMAN_ONLY`)
- **Назначение:** Классический режим Helpdesk / контакт-центра без участия искусственного интеллекта.
- **Поведение системы:**
  - При поступлении нового обращения диалог сразу создается в статусе ожидания живого специалиста (`ControlMode.PAUSED`, `ExpectedResponder.OPERATOR`).
  - Фиксируется точное время начала ожидания (`waiting_since`).
  - Диалог появляется в папке «Ожидают ответа» у всех дежурных операторов канала или привязанной группы.
  - Генерация ответа через внешние LLM-провайдеры **не инициируется**, экономя бюджет на токены и исключая риски галлюцинаций.
- **Рекомендации к применению:** Юридические и финансовые консультации, VIP-линии, каналы сложных технических инцидентов, каналы прямых продаж.

#### 2. По правилам / Гибридный (`RULE_BASED`)
- **Назначение:** Интеллектуальное распределение потока обращений на основе набора настраиваемых условий.
- **Поведение системы:**
  - Каждое входящее событие (создание нового обращения или сообщение в открытый диалог) направляется в модуль **Rules Engine**.
  - Правила канала проверяются последовательно сверху вниз по приоритету (`priority ASC`).
  - Первое подошедшее правило определяет маршрут: ответ AI, постановка в очередь операторов или перевод на специализированную группу.
  - Если ни одно правило не совпало — срабатывает защитное дефолтное правило (переход к операторам).
- **Рекомендации к применению:** Круглосуточная поддержка со сменами (днем — люди, ночью — бот), сегментация входящего трафика (простые вопросы — боту, претензии и оптовики — профильным отделам).

#### 3. ИИ-агент по умолчанию (`AI_FIRST`)
- **Назначение:** Максимальная автоматизация первой линии поддержки.
- **Поведение системы:**
  - Если на канале назначен и активен виртуальный ассистент (`AIAgent`), он мгновенно формирует ответ клиенту по базе знаний.
  - Перевод в очередь операторов происходит только при срабатывании триггеров эскалации (клиент просит человека, бот не нашел информацию в базе знаний, зафиксирована жалоба или технический сбой).
- **Рекомендации к применению:** Высоконагруженные справочные службы, интернет-магазины в периоды распродаж, стандартные FAQ-сценарии.

### 2.2. Настройка расписания работы (Business Hours) и часовых поясов

Для каналов, работающих в режиме `RULE_BASED` или использующих уведомления о нерабочих часах, супервайзер настраивает график доступности операторов.

Настройка расположена:  
`Панель управления` → `Каналы связи` → Выберите канал → вкладка `График работы`.

#### Шаги настройки:
1. **Выбор часового пояса (`Timezone`):**  
   Укажите часовой пояс, по которому работает дежурная смена канала (например, `Europe/Moscow`, `Asia/Yekaterinburg`, `Asia/Almaty`). Все расчеты рабочего времени производятся относительно выбранного пояса с автоматическим учетом сезонного времени.
2. **Заполнение недельной сетки (`Weekly Schedule`):**  
   Для каждого дня недели (Пн–Вс):
   - Отметьте день как рабочий или выходной.
   - Задайте интервал работы в формате `ЧЧ:ММ` (например, `09:00 – 18:00`).
   - При необходимости добавьте обеденный перерыв (например, интервал 1: `09:00 – 13:00`, интервал 2: `14:00 – 18:00`).
3. **Календарь праздничных и нерабочих дней (`Holidays`):**  
   Добавьте индивидуальные даты государственных праздников или корпоративных выходных (в формате `ГГГГ-ММ-ДД`). В эти дни график работы автоматически приравнивается к нерабочему, даже если день недели отмечен как рабочий.
4. **Обработка незаполненного расписания:**  
   Если график не задан или отключен, движок правил трактует условие «В рабочие часы» как `false` (нерабочее время) и записывает предупреждение в журнал настроек. Система продолжает стабильную работу без сбоев.

### 2.3. Пошаговое создание и настройка правил маршрутизации (Rules Engine)

Модуль правил позволяет гибко управлять распределением диалогов. Чтобы перейти к настройке:  
`Панель управления` → `Каналы связи` → Выберите канал → вкладка `Правила маршрутизации`.

#### Анатомия правила маршрутизации:
Каждое правило состоит из пяти базовых атрибутов:
1. **Название правила (`Name`):** Понятное описание бизнес-логики (например, «VIP-клиенты напрямую старшим специалистам»).
2. **Приоритет (`Priority`):** Целое положительное число от `1` до `1000`. Чем меньше число, тем выше приоритет. Правило с приоритетом `10` проверяется раньше правила с приоритетом `50`.
3. **Статус активности (`is_active`):** Переключатель, позволяющий временно отключить правило без его удаления.
4. **Триггерное событие (`Trigger Event`):**
   - `Создание диалога (CONVERSATION_CREATED)` — срабатывает при открытии нового обращения от клиента (основная точка входа).
   - `Входящее сообщение (MESSAGE_RECEIVED)` — срабатывает на каждое сообщение, позволяя перехватить диалог посреди разговора с ботом.
5. **Дерево условий (`Conditions`):** Набор логических предикатов.
6. **Целевое действие (`Action Target`):** Куда отправить диалог при выполнении условий.

```
┌────────────────────────────────────────────────────────────────────────┐
│                        КАРТОЧКА ПРАВИЛА                                │
├────────────────────────────────────────────────────────────────────────┤
│ Название: VIP и претензии без очереди                                  │
│ Приоритет: 10 | Статус: [ Активно ] | Триггер: Создание диалога        │
├────────────────────────────────────────────────────────────────────────┤
│ ЕСЛИ ВЫПОЛНЯЕТСЯ [ ХОТЯ БЫ ОДНО (ANY) ]:                               │
│  ├── Метка контакта содержит "VIP"                                     │
│  └── Текст сообщения содержит любое из: "претензия", "суд", "возврат"  │
├────────────────────────────────────────────────────────────────────────┤
│ ТОГДА ДЕЙСТВИЕ:                                                        │
│  ● Направить операторам                                                │
│  Целевая группа: Старшая линия поддержки                               │
└────────────────────────────────────────────────────────────────────────┘
```

#### Доступные предикаты и параметры условий:

| Категория | Параметр | Поддерживаемые операторы | Описание и пример |
| :--- | :--- | :--- | :--- |
| **График работы** | `schedule.is_working_hours` | `eq` (равно), `neq` (не равно) | `true` — сообщение пришло в рабочее время канала; `false` — вне графика или в праздник. |
| **Клиент** | `contact.labels` | `contains` (содержит), `not_contains` | Проверка ярлыков клиента (например: `VIP`, `Партнер`, `Оптовик`). |
| **Клиент** | `contact.has_phone` | `eq` (равно) | Проверка, подтвержден ли номер телефона (`true`/`false`). |
| **Диалог** | `conversation.is_first_message` | `eq` (равно) | `true` — клиент пишет в компанию впервые за все время. |
| **Текст** | `message.text_contains` | `contains_any` (любое из), `contains_all` (все) | Поиск стоп-слов без учета регистра (регистронезависимо). Пример: `претензия, жалоба, расторжение`. |
| **Текст** | `message.regex_match` | `regex` (соответствие RegExp) | Проверка по регулярному выражению (номер договора `^ДОГ-\d{6}$`, трек-номер посылки). |
| **Канал** | `channel.routing_mode` | `eq` (равно) | Проверка типа режима канала. |

#### Логические блоки условий:
- **`all` (логическое «И»):** Действие выполняется только в том случае, если выполнены **все** указанные условия.
- **`any` (логическое «ИЛИ»):** Действие выполняется, если выполнено **хотя бы одно** из условий.
- **`not` (логическое отрицание):** Инверсия вложенного условия.

#### Доступные целевые действия (`Action Target`):
1. **Направить ИИ-агенту (`ROUTE_TO_AI`):**  
   Диалог переходит в ведение виртуального ассистента (`ControlMode.AI`). Ассистент генерирует ответ на основе подключенной к каналу базы знаний.
2. **Направить в очередь операторов (`ROUTE_TO_HUMAN`):**  
   Диалог ставится в общую очередь свободных операторов канала (`ControlMode.PAUSED`). ИИ не отвечает.
3. **Назначить группу операторов (`ASSIGN_GROUP`):**  
   Диалог ставится в очередь конкретного подразделения (например, «Бухгалтерия», «Отдел продаж», «Претензионный отдел»). Поле `target_group` обязательно для заполнения.
4. **Игнорировать / Спам (`DROP_SILENTLY`):**  
   Служебное действие для отсечения очевидного спама или вредоносных рассылок без уведомления операторов и без расхода токенов.

### 2.4. Примеры практических сценариев настройки

#### Сценарий А: «ИИ ночью и в выходные, живые специалисты днем»
- **Цель:** Обеспечить мгновенные ответы клиентам 24/7, не оплачивая ночные смены операторов.
- **Настройка расписания:** Пн–Пт с 09:00 до 18:00 (МСК), суббота и воскресенье — выходные.
- **Правило 1 (Приоритет 100):**
  - **Условие:** `schedule.is_working_hours == true`
  - **Действие:** `Направить в очередь операторов`
- **Правило 2 (Приоритет 200):**
  - **Условие:** `schedule.is_working_hours == false`
  - **Действие:** `Направить ИИ-агенту`
- **Результат:** Днем все клиенты попадают операторам. Ровно в 18:01 эстафету автоматически перехватывает ИИ.

#### Сценарий Б: «VIP-клиенты и претензии — сразу старшим специалистам»
- **Цель:** Не допустить раздражения премиум-клиентов и клиентов в конфликтном состоянии ответами бота.
- **Правило 1 (Приоритет 10):**
  - **Условие (ANY):**  
    `contact.labels` содержит `VIP` **ИЛИ**  
    `message.text_contains` содержит любое из: `жалоба, претензия, суд, неустойка, директор`
  - **Действие:** `Назначить группу операторов` → `Старшая линия поддержки`
- **Правило 2 (Приоритет 50):**
  - **Условие:** `conversation.is_first_message == true`
  - **Действие:** `Направить ИИ-агенту` (первичная квалификация лида ботом)
- **Результат:** Если VIP-клиент пишет даже просто «Привет», он мгновенно попадает к человеку. Если обычный клиент пишет о претензии — он сразу переводится на старшую смену.

### 2.5. Правило по умолчанию (Default Fallback) и защита от потери обращений

Платформа Chatballs обеспечивает непрерывную надежность обработки входящих обращений на нескольких уровнях:

1. **Безусловный Default Fallback Rules Engine:**
   - Если в канале с режимом `RULE_BASED` ни одно из настроенных правил не совпало с параметрами сообщения (или список правил пуст), система **гарантированно направляет диалог в очередь операторов** (`ROUTE_TO_HUMAN`).
   - Потеря или «зависание» диалога архитектурно исключены.
2. **Тихий Fallback при сбое LLM-провайдера:**
   - Если диалог был направлен ИИ-агенту, но внешний провайдер нейросетей возвращает ошибку (HTTP 500/502/503), ошибку превышения лимитов (HTTP 429), не укладывается в таймаут 15 секунд или исчерпан лимит баланса токенов (BYOK):
     * Диалог **тихо и автоматически** эскалируется в очередь операторов.
     * Клиенту **не показываются** технические ошибки, стектрейсы или предупреждения об ошибках шлюза.
     * В карточке диалога для оператора выставляется служебный индикатор: *«Диалог передан оператору в связи со сбоем LLM»*.
3. **Защита от удаления групп операторов:**
   - Если группа операторов, указанная в правиле, была удалена или расформирована, диалог не блокируется, а направляется в общий пул операторов текущего канала связи (`on_delete=SET_NULL`).

## 3. Руководство оператора поддержки

Данный раздел предназначен для специалистов первой и второй линии клиентской поддержки, работающих в едином окне диалогов Chatballs.

### 3.1. Индикаторы статуса диалога

В рабочей области оператора в шапке каждого открытого тикета отображается цветовой бейдж текущего состояния:

| Бейдж | Цвет | Значение | Что происходит |
| :--- | :--- | :--- | :--- |
| **ИИ-агент** | 🟣 Фиолетовый | Диалог ведет бот | ИИ самостоятельно генерирует ответы клиенту по базе знаний. Оператор может наблюдать за беседой в режиме реального времени. |
| **В очереди** | 🟡 Желтый | Ожидает человека | Клиент ждет ответа свободного специалиста. В карточке тикета отображается таймер времени ожидания (`waiting_since`). |
| **Вы** | 🟢 Зеленый | Закреплен за вами | Диалог перехвачен вами. Все ответы клиента поступают лично вам. ИИ полностью отключен. |
| **[Имя коллеги]** | ⚪ Серый | Закреплен за коллегой | Диалог находится в работе у другого сотрудника смены. |

---

### 3.2. Механика мгновенного перехвата диалога (Interception)

Если оператор видит, что клиент задает сложный вопрос, проявляет недовольство или бот затрудняется с формулировкой, оператор может перехватить управление **мгновенно двумя способами**:

#### Способ 1: Прямая отправка сообщения (Рекомендуемый)
1. Откройте чат с клиентом, который в данный момент ведет ИИ.
2. В поле ввода отображается информационная подсказка:  
   *«Отправка сообщения автоматически переведет диалог на вас»*.
3. Наберите ответ клиенту и нажмите кнопку «Отправить» (или клавишу `Enter`).
4. **Что происходит в системе:**
   - В момент отправки диалог **синхронно переключается** в режим обслуживания человеком (`ControlMode.HUMAN`).
   - Если в этот же момент нейросеть вычисляла ответ в фоне, этот ответ **автоматически аннулируется и блокируется**.
   - Клиент получает только ответ живого оператора без задвоения реплик.

#### Способ 2: Кнопка «Взять диалог»
1. В верхней панели диалога нажмите кнопку **«Взять диалог»**.
2. Бейдж статуса мгновенно сменится на зеленый («Вы»).
3. Бот прекращает участие в переписке, а диалог закрепляется за вашей учетной записью.

---

### 3.3. Механика возврата диалога ИИ-агенту (Return to AI)

Если оператор помог клиенту с нестандартным или сложным вопросом, а дальнейшее общение носит типовой характер (например, уточнение графика работы складов, оформление типовой заявки или опрос качества обслуживания NPS), диалог можно вернуть виртуальному ассистенту:

1. В шапке открытого диалога нажмите кнопку дополнительных действий `···` (или кнопку **«Передать ИИ»**).
2. Выберите пункт **«Передать ИИ-агенту»**.
3. В появившемся модальном окне подтвердите действие.
4. **Что происходит в системе:**
   - Статус диалога переключается в `ControlMode.AI`, бейдж становится фиолетовым.
   - Закрепление за конкретным оператором снимается.
   - Следующее сообщение клиента будет принято и обработано ИИ-агентом.
   - История переписки сохраняется: ИИ видит предыдущие ответы оператора и учитывает их контекст.

---

### 3.4. Автоматическая эскалация к оператору

ИИ-агент автоматически передаст диалог в очередь специалистов, если зафиксирует:
- **Явную просьбу клиента:** фразы вроде *«позови человека»*, *«соедини с оператором»*, *«переведи на менеджера»*.
- **Отсутствие ответа в базе знаний:** если релевантность найденных материалов ниже порога уверенности модели.
- **Повторяющиеся вопросы:** если клиент 2 раза подряд переспрашивает одно и то же.
- **Жалобы и юридические претензии:** при наличии настроенных правил по стоп-словам.

При эскалации диалог переходит в желтый статус («В очереди»), а в ленте отображается сервисная заметка о причине передачи.

## 4. Релиз-ноут и спецификация API

Раздел предназначен для разработчиков, интеграторов и DevOps-инженеров, настраивающих автоматизацию и интеграцию каналов связи Chatballs с внешними CRM и Helpdesk-системами.

### 4.1. Обзор релиза (Release Notes v1.1.0 — Flexible Routing & Rules Engine)

#### Главные новшества:
- **Отказ от обязательного AI-First:** каналы связи теперь поддерживают полноценный режим `HUMAN_ONLY`.
- **Встроенный Rules Engine:** модуль декларативной проверки условий входящих обращений на базе приоритетов и JSON-дерева предикатов.
- **Управление расписанием (Business Hours):** поддержка часовых поясов, расписаний с перерывами и списков праздничных дат.
- **Zero-Drop Fallback:** гарантированная доставка диалогов операторам при сбоях внешних поставщиков LLM или отсутствии совпадений в правилах.
- **Защита от состояния гонки (Race Condition):** синхронная отмена генерации ответа модели при отправке сообщения сотрудником.

---

### 4.2. Спецификация REST API

Все запросы к API требуют передачи авторизационного заголовка:  
`Authorization: Bearer <API_TOKEN>`  
Формат обмена данными: `application/json`.

---

#### 1. Изменение режима маршрутизации канала
Позволяет изменить стратегию распределения сообщений для заданного канала.

- **Метод:** `PATCH`
- **Эндпоинт:** `/api/channels/{channel_id}/`
- **Тело запроса:**
```json
{
  "routing_mode": "RULE_BASED"
}
```
- **Допустимые значения `routing_mode`:**
  - `AI_FIRST` — ИИ отвечает первым;
  - `HUMAN_ONLY` — Только операторы, ИИ отключен;
  - `RULE_BASED` — Маршрутизация по правилам.

- **Успешный ответ (`200 OK`):**
```json
{
  "id": "c1f78e4a-2e65-4b13-9f12-08149d85bf10",
  "name": "Основной Telegram-канал",
  "transport_type": "telegram",
  "routing_mode": "RULE_BASED",
  "is_active": true,
  "updated_at": "2026-09-24T12:00:00Z"
}
```

#### 5. Создание нового правила маршрутизации
- **Метод:** `POST`
- **Эндпоинт:** `/api/channels/{channel_id}/routing-rules/`
- **Тело запроса:**
```json
{
  "name": "VIP клиенты и жалобы напрямую старшим",
  "description": "Эскалация по стоп-словам и метке VIP",
  "priority": 10,
  "is_active": true,
  "trigger_event": "CONVERSATION_CREATED",
  "conditions": {
    "any": [
      {"field": "contact.labels", "op": "contains", "value": "VIP"},
      {"field": "message.text_contains", "op": "contains_any", "value": ["жалоба", "претензия", "суд"]}
    ]
  },
  "action_target": "ROUTE_TO_HUMAN",
  "target_group_id": 4
}
```
- **Параметры полей:**
  - `name` (string, обязательное): название правила.
  - `priority` (integer, обязательное): приоритет проверки (меньше = выше).
  - `is_active` (boolean, опционально, default: `true`).
  - `trigger_event` (string, choices: `CONVERSATION_CREATED`, `MESSAGE_RECEIVED`).
  - `conditions` (object, обязательное): декларативная структура условий.
  - `action_target` (string, choices: `ROUTE_TO_AI`, `ROUTE_TO_HUMAN`, `ASSIGN_GROUP`, `DROP_SILENTLY`).
  - `target_group_id` (integer/null, опционально): ID группы операторов (обязательно при `action_target = ASSIGN_GROUP`).

- **Успешный ответ (`201 Created`):** Возвращает созданную запись с присвоенным `id`.

---

#### 6. Обновление и удаление правила маршрутизации
- **Обновление правила:**
  - `PATCH /api/channels/{channel_id}/routing-rules/{rule_id}/` — частичное обновление.
  - `PUT /api/channels/{channel_id}/routing-rules/{rule_id}/` — полное обновление.
- **Удаление правила:**
  - `DELETE /api/channels/{channel_id}/routing-rules/{rule_id}/`
  - Ответ: `204 No Content`.

---

#### 7. Массовое изменение порядка приоритетов правил
Используется фронтенд-интерфейсом при drag-and-drop сортировке правил.

- **Метод:** `POST`
- **Эндпоинт:** `/api/channels/{channel_id}/routing-rules/reorder/`
- **Тело запроса:**
```json
{
  "rule_ids": [14, 12, 13]
}
```
- **Поведение:** Система автоматически назначает правила в переданном порядке приоритетов (`10, 20, 30...`).
- **Успешный ответ (`200 OK`):**
```json
{
  "status": "success",
  "updated_count": 3
}
```

### 4.3. Коды состояния и обработка ошибок

| HTTP Код | Описание ошибки | Пример решения |
| :--- | :--- | :--- |
| **`400 Bad Request`** | Ошибка валидации JSON-схемы условий или неверный `action_target`. | Проверьте формат полей в объекте `conditions` и наличие закрывающих скобок. |
| **`403 Forbidden`** | Недостаточно прав для управления каналом связи. | Требуется роль администратора организации или супервайзера. |
| **`404 Not Found`** | Канал связи или правило маршрутизации с указанным ID не найдены. | Проверьте корректность `channel_id` и `rule_id`. |
| **`422 Unprocessable`** | Попытка указать несуществующий `target_group_id` или группу из чужой организации. | Убедитесь, что группа сотрудников принадлежит вашей организации. |

## 5. Заключение

Внедрение гибких режимов маршрутизации и движка правил Rules Engine обеспечивает баланс между скоростью работы ИИ и контролем со стороны операторов. При возникновении дополнительных вопросов или предложений по развитию предикатов маршрутизации обращайтесь к технической команде Chatballs.
