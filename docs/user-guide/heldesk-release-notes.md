# Релизные заметки: новый раздел Heldesk

**Версия продукта:** 1.15.0
**Дата:** 25 сентября 2026 года
**Связанные задачи:** HOM-30, HOM-47, HOM-48, HOM-49, HOM-51
**Документация:** руководство оператора (`docs/user-guide/heldesk-operator-guide.md`), спецификация API (`docs/architecture/heldesk-api-spec.md`), руководство администратора (`docs/architecture/heldesk-admin-guide.md`)

---

## 1. Что нового

В продукте появился полноценный раздел «Заявки» (Heldesk) для ведения длительных обращений клиентов. Ранее диалог в чате был единственным местом работы, теперь у поддержки есть реестр заявок со статусами, приоритетами, ответственными, историей и уведомлениями.

Ключевые возможности релиза:

- реестр заявок с фильтрами, поиском, сортировкой и быстрой пагинацией;
- карточка заявки с переходами статусов, перепиской, внутренними заметками и историей;
- создание заявки из активного диалога, из карточки клиента и из реестра;
- разделение публичной переписки и скрытых заметок команды;
- режим «Не уведомлять клиента» для тихих внутренних действий;
- гостевые ссылки для просмотра статуса без входа в систему;
- гарантированная доставка уведомлений через транзакционный Outbox;
- мгновенное обновление интерфейса через WebSocket-сигнал без передачи персональных данных.

## 2. Возможности для операторов и руководителей

- **Жизненный цикл под контролем.** Статусы `Новая`, `В работе`, `Ожидание клиента`, `Решена`, `Закрыта`, а также `Отменена` и `Дубликат`. Недопустимые переходы заблокированы, для решения и отмены обязательно указывается причина.
- **Приоритеты.** Шкала `Низкий`, `Обычный`, `Высокий`, `Срочный` для triage очереди и контроля перегруза.
- **Создание из чата в один клик.** Кнопка «Создать заявку» в шапке диалога предзаполняет клиента и диалог, связывает заявку с обращением и обновляет блок «Связанные заявки».
- **Порядок в переписке.** Публичные комментарии уходят клиенту в его канал, внутренние заметки с иконкой замка остаются внутри команды и никогда не видны клиенту.
- **Тихий режим.** Переключатель «Не уведомлять клиента» с обязательной причиной позволяет фиксировать промежуточные действия без лишних сообщений клиенту. Причина сохраняется в истории.
- **Поиск и фильтры.** Фильтры по статусу, приоритету, ответственному, группе и заявителю, поиск по номеру и теме, сортировка по дате и приоритету.
- **Защита от потери изменений.** При одновременном редактировании система предупреждает о конфликте версий и предлагает обновить данные вместо перезаписи чужих изменений.

## 3. Возможности для инженеров и администраторов

- **Надёжное ядро `chatballs.tickets`.** Атомарная нумерация `TKT-000001`, оптимистическая блокировка, строгая машина состояний, аудит `TicketEvent`.
- **Строгая изоляция данных.** Политики PostgreSQL RLS и межарендные триггеры на всех связях. Данные одной организации недоступны другой даже при ошибке прикладного кода.
- **Гарантированная доставка.** Очередь `TicketDelivery` со статусами `PENDING`, `SENT`, `FAILED`, `SUPPRESSED`, `UNCERTAIN`, дедупликацией по событию и адресу, повторами с экспоненциальной задержкой.
- **Раздельные потоки уведомлений.** Внутренние уведомления сотрудникам не зависят от подавления клиентских. Внешние сообщения уходят только в привязанный диалог клиента.
- **Наблюдаемость.** Очередь диагностируется обычными SQL-запросами по статусу и каналу, причины ошибок фиксируются в `last_error`, причины подавления — в истории событий.

Полные технические детали приведены в спецификации API и руководстве администратора (см. ссылки выше).

## 4. Изменения и совместимость

- Добавлены новые таблицы `tickets_*` и политики RLS. Существующие диалоги, контакты и каналы не изменяются. Удаление диалога больше не удаляет связанную заявку: связь сохраняется как пустая ссылка, история заявки остаётся.
- Добавлены новые полномочия `tickets.view` и `tickets.manage`. Доступ к разделу нужно выдать ролям операторов и руководителей. Без полномочий пункт «Заявки» скрыт.
- Добавлен WebSocket-сигнал `tickets.inbox.changed` в существующем канале `/ws/organizations/{uuid}/conversations/`. Сигнал не содержит персональных данных и требует только перезапроса REST-данных.
- Добавлены гостевые маршруты `/api/v1/help/tickets/...`. По умолчанию токены деактивированы до первого выпуска из карточки заявки.
- Изменений в формате существующих сообщений чата нет. Миграции применяются штатно вместе с обновлением.

## 5. Обновление и первые шаги

1. Примените миграции и убедитесь, что политики RLS созданы без конфликтов.
2. Выдайте роли операторов и руководителей полномочия `tickets.view` и `tickets.manage`.
3. Проверьте настройки раздела на организацию: префикс номеров, категорию по умолчанию, срок автозакрытия.
4. Проверьте живость фонового воркера Outbox и доступность транспортов каналов.
5. Создайте тестовую заявку из диалога, добавьте комментарий и внутреннюю заметку, проверьте смену статусов и тихий режим.
6. Ознакомьте смену с руководством оператора, особенно с правилами разделения переписки и порядком указания причин.

## 6. Известные ограничения

- Переходы из финальных статусов (`Закрыта`, `Отменена`, `Дубликат`) запрещены. Ошибочно закрытую заявку нельзя переоткрыть, необходимо создать новую со ссылкой на исходную.
- Гостевой доступ показывает только публичную часть. Внутренние заметки и служебная история гостю недоступны по дизайну.
- Обязательные сервисные уведомления подавить нельзя. Попытка подавления таких событий отклоняется.
