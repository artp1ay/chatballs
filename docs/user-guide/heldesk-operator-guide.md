# Руководство оператора и руководителя поддержки раздела Heldesk

**Версия документации:** 1.0
**Версия продукта:** 1.15.0
**Статус:** Действующая документация
**Связанные задачи:** HOM-30, HOM-33, HOM-47, HOM-48, HOM-49
**Аудитория:** операторы первой и второй линии, руководители групп поддержки, супервайзеры

---

## 1. Назначение раздела

Раздел «Заявки» (Heldesk) — это реестр длительных обращений клиентов, которые нельзя закрыть одним диалогом в чате. Заявка объединяет тему, приоритет, ответственного, переписку с клиентом, внутренние заметки команды и историю изменений.

Основные сценарии:

- зафиксировать проблему клиента из активного диалога и вести её до решения;
- создать заявку вручную из реестра или из карточки клиента;
- вести публичную переписку с клиентом и скрытые внутренние обсуждения в одной карточке;
- контролировать сроки и нагрузку через статусы, приоритеты, фильтры и поиск.

Пункт меню: «Заявки». Маршруты интерфейса: `/tickets` (реестр), `/tickets/:id` (карточка заявки).

Доступ к разделу определяется полномочиями: чтение — `tickets.view`, создание и изменение — `tickets.manage`. Руководители и операторы с соответствующими полномочиями видят одни и те же экраны, различие только в доступных действиях.

## 2. Жизненный цикл заявки

### 2.1. Статусы

| Статус | Название в интерфейсе | Смысл |
|---|---|---|
| `NEW` | Новая | Заявка только создана, работа ещё не начата. |
| `IN_PROGRESS` | В работе | Оператор или группа взяли заявку в работу. |
| `WAITING_CUSTOMER` | Ожидание клиента | Нужен ответ или действие клиента. Работа со стороны поддержки приостановлена. |
| `RESOLVED` | Решена | Решение найдено и зафиксировано. Ожидается подтверждение клиента или автозакрытие. |
| `CLOSED` | Закрыта | Финальное состояние. Изменения запрещены. |
| `CANCELLED` | Отменена | Заявка закрыта без решения (ошибочная, неактуальная). Требуется причина. |
| `DUPLICATE` | Дубликат | Заявка повторяет другую заявку. Требуется причина или ссылка на исходную заявку. |

### 2.2. Разрешённые переходы

Перевести заявку можно только по разрешённым связям. Недопустимый переход отклоняется с ошибкой `invalid_transition`.

- Из `NEW`: в `IN_PROGRESS`, `CANCELLED`, `DUPLICATE`.
- Из `IN_PROGRESS`: в `WAITING_CUSTOMER`, `RESOLVED`, `CANCELLED`, `DUPLICATE`.
- Из `WAITING_CUSTOMER`: в `IN_PROGRESS`, `RESOLVED`, `CANCELLED`, `DUPLICATE`.
- Из `RESOLVED`: в `IN_PROGRESS` (повторное открытие), `CLOSED`, `CANCELLED`, `DUPLICATE`.
- Из `CLOSED`, `CANCELLED`, `DUPLICATE`: переходы запрещены. Это финальные состояния.

Схема:

```text
NEW → IN_PROGRESS → WAITING_CUSTOMER → IN_PROGRESS → RESOLVED → CLOSED
         ↓                ↓                 ↓            ↓
     CANCELLED/       CANCELLED/        CANCELLED/   CANCELLED/
     DUPLICATE        DUPLICATE         DUPLICATE    DUPLICATE
```

Возврат из `RESOLVED` в `IN_PROGRESS` используется, когда клиент не подтвердил решение или проблема возобновилась. При этом отметка о решении снимается.

### 2.3. Приоритеты

| Приоритет | Название | Когда использовать |
|---|---|---|
| `LOW` | Низкий | Вопрос без срочности: пожелание, уточнение, косметический дефект. |
| `NORMAL` | Обычный | Стандартное обращение. Значение по умолчанию. |
| `HIGH` | Высокий | Клиент заблокирован частично, есть обходной путь, но требуется ускорение. |
| `URGENT` | Срочный | Полная блокировка, финансовые потери, массовый сбой. |

Приоритет можно менять в любой момент через редактирование карточки. Смена приоритета фиксируется в истории событий.

### 2.4. Номер заявки и версия

- Каждой заявке присваивается номер вида `TKT-000104`. Префикс настраивается на организацию (по умолчанию `TKT`), счётчик уникален в пределах организации.
- Поле `version` защищает от потери изменений при совместной работе. При смене статуса и редактировании интерфейс передаёт текущую версию (`expected_version`). Если заявку уже изменил другой оператор, сервер возвращает ошибку `409 Conflict` с текстом «Заявка была изменена другим пользователем». В этом случае обновите карточку и повторите действие, не перезаписывая чужие изменения.

## 3. Создание заявки

### 3.1. Создание из реестра

1. Откройте раздел «Заявки» и нажмите «Создать заявку».
2. Заполните обязательное поле «Тема» (например, «Не работает оплата по СБП»).
3. При необходимости заполните описание, приоритет (по умолчанию «Обычный»), категорию (по умолчанию `general`).
4. Укажите клиента (контакт заявителя), ответственного сотрудника и группу.
5. Сохраните. Система присвоит номер и откроет карточку заявки.

### 3.2. Создание из активного диалога чата

Этот способ предпочтителен, когда обращение уже идёт в чате.

1. Откройте диалог в рабочем месте оператора.
2. В шапке диалога нажмите кнопку «Создать заявку».
3. В модальном окне проверьте предзаполненные данные: клиент подставляется из контакта диалога, исходный диалог сохраняется как `origin_conversation`.
4. Уточните тему (по умолчанию подставляется краткое содержание диалога), описание, приоритет, категорию, ответственного и группу.
5. Сохраните. Система создаст заявку, привяжет её к диалогу через связь `TicketConversationLink` и зафиксирует событие `CREATED_FROM_CONVERSATION`.
6. После создания появляется уведомление с номером заявки, а блок «Связанные заявки» в контекстной панели диалога обновляется.

Технический маршрут для этого действия: `POST /api/v1/conversations/{conversation_id}/ticket/`.

### 3.3. Создание из карточки клиента

1. Откройте карточку контакта клиента (из диалога или из поиска контактов).
2. В блоке «Заявки клиента» нажмите «Новая заявка».
3. Проверьте, что заявитель подставлен корректно. Остальные поля заполняются так же, как при создании из реестра.
4. Сохраните. Новая заявка появится в списке связанных заявок клиента.

### 3.4. Блок «Связанные заявки»

В контекстной панели диалога под данными контакта отображается секция «Заявки клиента»:

- заголовок с числом активных заявок;
- компактный список: номер, тема, текущий статус, дата;
- переход в карточку заявки по клику;
- кнопка создания новой заявки.

Блок помогает избежать дублей: перед созданием заявки проверьте, нет ли уже активной заявки по той же проблеме. Если есть, используйте существующую.

## 4. Ведение переписки

В карточке заявки три вкладки: «Переписка с клиентом», «Внутренние заметки», «История изменений».

### 4.1. Публичные комментарии

Публичный комментарий — это сообщение, которое видит клиент (в привязанном канале: электронная почта, Telegram, VK, MAX, веб-чат) и которое сохраняется в истории заявки.

Правила:

- Пишите от имени компании, а не от себя лично. Клиент видит текст, а не служебные детали.
- Один комментарий — одна завершённая мысль или вопрос. Не объединяйте решение и новый запрос документов в один абзац без структуры.
- Комментарий оператора создаёт событие `COMMENT_ADDED` и по умолчанию ставит клиента в очередь на уведомление.
- Комментарии клиента, поступившие через гостевую ссылку или привязанный диалог, также отображаются в этой вкладке.
- Флаг `is_public` у обычных комментариев всегда включён. Непубличное обсуждение ведите во внутренних заметках, а не в переписке.

Как добавить комментарий:

1. Откройте вкладку «Переписка с клиентом».
2. Введите текст в поле ввода.
3. Проверьте состояние переключателя «Не уведомлять клиента» (см. раздел 5).
4. Отправьте. Комментарий появится в списке с именем автора и временем.

Пустой текст отклоняется с ошибкой `comment_text_required`.

### 4.2. Внутренние заметки команды

Внутренняя заметка видна только сотрудникам с доступом к заявкам. Клиент никогда её не видит, уведомления клиенту по заметкам не отправляются.

Используйте заметки для:

- гипотез и результатов диагностики («Проверил логи, ошибка 500 только при оплате СБП»);
- договорённостей внутри смены («Дождаться ответа биллинга до 15:00, потом позвонить клиенту»);
- передачи контекста при смене ответственного.

Визуально заметки выделены (плашка с иконкой замка), чтобы их нельзя было перепутать с перепиской. Пустой текст отклоняется с ошибкой `note_text_required`.

### 4.3. Что куда писать

| Ситуация | Куда писать |
|---|---|
| Вопрос клиенту, ответ, инструкция, подтверждение решения | Публичный комментарий |
| Обсуждение между операторами, черновик ответа, диагностика | Внутренняя заметка |
| Фиксация факта смены статуса, назначения, смены приоритета | Автоматически в историю, вручную дублировать не нужно |

## 5. Режим «Не уведомлять клиента»

### 5.1. Назначение

По умолчанию каждое публичное действие (комментарий, смена статуса, создание заявки) ставит клиенту уведомление в его канал. Переключатель «Не уведомлять клиента» временно отключает внешнее уведомление для одного конкретного действия, не затрагивая внутренние уведомления сотрудникам.

Используйте режим в случаях:

- техническое промежуточное действие, о котором клиента уведомлять рано (например, перевод в `IN_PROGRESS` сразу после создания);
- массовая выверка статусов, дополнение истории задним числом;
- комментарий-черновик, который должен остаться в истории, но не должен уходить клиенту сейчас.

Не используйте режим, чтобы скрыть от клиента важное изменение решения или сроков. Если клиент должен знать — уведомление должно уйти.

### 5.2. Как пользоваться

В форме комментария:

1. Введите текст комментария.
2. Включите переключатель «Не уведомлять клиента».
3. При появлении поля причины подавления укажите короткую причину (например, «Промежуточная пометка, ответ клиенту уйдёт после проверки биллинга»). Без причины сервер вернёт ошибку `suppression_reason_required`.
4. Отправьте комментарий.

При смене статуса:

1. Нажмите кнопку целевого статуса.
2. В модальном окне укажите обязательную причину перехода (для `RESOLVED`, `CANCELLED`, `DUPLICATE` — обязательно, для остальных — рекомендуется).
3. Если нужно подавить уведомление, выберите политику «Не уведомлять» и укажите причину подавления.
4. Подтвердите переход.

### 5.3. Что происходит при подавлении

- Внешнее сообщение в канал клиента не отправляется.
- В очереди доставок создаётся запись со статусом `SUPPRESSED` и указанной причиной.
- В историю заявки (`TicketEvent`) записывается событие с признаком `notify_customer = false` и текстом причины.
- Внутренние уведомления сотрудникам (о новой заявке, назначении, смене статуса, ответе клиента) отправляются в обычном порядке и от подавления не зависят.

Подавить обязательные транзакционные и сервисные события нельзя: система отклонит такую попытку на уровне доменной логики.

## 6. Работа со списком, фильтрами и поиском

### 6.1. Реестр заявок

Таблица реестра содержит колонки: номер (ссылка на карточку), тема, клиент, статус, приоритет, группа и ответственный, дата обновления. При загрузке отображаются индикаторы загрузки, при отсутствии результатов — состояние «Заявки не найдены» с предложением сбросить фильтры или создать заявку.

### 6.2. Фильтры

Панель фильтров над таблицей:

- статус — выбор одного или нескольких значений через запятую (например, `NEW,IN_PROGRESS`) или «Все статусы»;
- приоритет — аналогично, через запятую;
- ответственный (`assignee_id`) — фильтр по сотруднику;
- группа (`group_id`) — фильтр по рабочей группе;
- заявитель (`requester_id`) — фильтр по контакту клиента.

Кнопка «Сбросить фильтры» возвращает список к полному реестру.

### 6.3. Поиск

Строка поиска (параметр `search`) ищет одновременно:

- по номеру заявки (частичное совпадение, например, `TKT-0001` найдёт `TKT-000104`);
- по подстроке в теме заявки.

Поиск работает совместно с фильтрами: сначала применяются фильтры, затем поисковая подстрока.

### 6.4. Сортировка и пагинация

- Сортировка: `created_at` (по умолчанию, новые сверху), `updated_at`, `priority`. Направление задаётся префиксом `-` (например, `sort=-updated_at`). Для стабильности в конец всегда добавляется сортировка по идентификатору.
- Пагинация курсорная (keyset): параметры `after` (курсор) и `window_size` (размер страницы, обычно 20, 50 или 100). Ответ содержит `items`, `total`, `next_cursor`, `has_more`.

### 6.5. Типовые выборки руководителя

- «Новые без ответственного»: фильтр `status=NEW`, ответственный не задан — для разбора очереди.
- «Срочные в работе»: фильтр `priority=URGENT`, `status=IN_PROGRESS,WAITING_CUSTOMER` — для контроля перегруза.
- «Зависшие в ожидании клиента»: фильтр `status=WAITING_CUSTOMER`, сортировка по `updated_at` — для пинга клиентов.
- «Поиск по номеру из письма клиента»: вставьте номер в строку поиска.

## 7. Смена статуса и редактирование

### 7.1. Смена статуса

1. Откройте карточку заявки.
2. В шапке отображаются только допустимые целевые статусы согласно разделу 2.2. Недопустимые кнопки не отображаются.
3. Нажмите целевой статус. Для `RESOLVED`, `CLOSED`, `CANCELLED` откроется модальное окно с обязательным полем причины.
4. Укажите причину решения, отмены или признак дубликата. Для дубликата укажите номер исходной заявки в причине.
5. При необходимости добавьте сопроводительный комментарий прямо из окна перехода.
6. Подтвердите. Карточка обновится, событие попадёт в историю.

При конфликте версий (`409 Conflict`) появится предупреждение «Заявка была изменена другим оператором». Нажмите «Обновить данные», проверьте чужие изменения и повторите переход.

### 7.2. Редактирование полей

Редактируются: тема, описание, категория, приоритет, ответственный, группа. Смена заявителя через редактирование не выполняется, заявитель фиксируется при создании.

Редактирование также передаёт `expected_version`. При расхождении версий сервер возвращает `409 Conflict` с текущим номером версии.

### 7.3. Гостевой доступ

Руководитель или оператор с правом `tickets.manage` может выпустить гостевую ссылку для клиента без входа в систему: действие «Публичный доступ» в карточке заявки создаёт токен (`POST .../public-access/`). Клиент по токену видит статус и публичную переписку, но не видит внутренние заметки. При истечении срока или деактивации токена гостевой просмотр возвращает ошибку `public_ticket_not_found`.

## 8. Типовые ошибки и действия

| Сообщение | Причина | Действие |
|---|---|---|
| «Заявка была изменена другим пользователем» (`version_conflict`, 409) | Карточку изменил другой оператор | Обновите страницу и повторите действие |
| «Недопустимый переход заявки из … в …» (`invalid_transition`, 400) | Статус пытаются перевести по запрещённой связи | Выберите допустимый целевой статус из раздела 2.2 |
| «Укажите причину отмены/дублирования/решения» (400) | Не заполнено обязательное поле причины | Заполните причину в модальном окне |
| «Укажите причину отключения уведомления клиента» (400) | Включён режим «Не уведомлять», но причина не указана | Укажите короткую причину подавления |
| «Заявка не найдена» (`not_found`, 404) | Неверный идентификатор или чужая организация | Проверьте номер и фильтр организации |
| «Недостаточно прав» (403) | Нет полномочия `tickets.view` или `tickets.manage` | Обратитесь к администратору за ролью |

## 9. Контрольный список для руководителя смены

1. Разобраны все заявки `NEW` без ответственного.
2. Нет заявок `URGENT` без движения дольше согласованного срока.
3. Заявки `WAITING_CUSTOMER` с просроченным ожиданием пропингованы или переведены обратно в `IN_PROGRESS`.
4. Причины решения и отмены заполнены содержательно, а не формально.
5. Внутренние заметки не содержат текста, предназначенного клиенту, и наоборот.
6. Подавления уведомлений имеют внятные причины в истории.
