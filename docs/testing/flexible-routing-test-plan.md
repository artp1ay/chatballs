## 1. Введение и цели контроля качества

### 1.1. Контекст перехода платформы
Исторически ядро обработки входящих сообщений Chatballs (`ingest_inbound`) функционировало в парадигме жесткого «AI-first по умолчанию»: любое входящее обращение безусловно перехватывалось LLM-агентом при его наличии на канале.

В рамках архитектурного решения [HOM-11](/HOM/issues/HOM-11) и продуктовых требований [HOM-10](/HOM/issues/HOM-10) платформа переходит на трехуровневую гибридную модель:
1. **«Только операторы» (`HUMAN_ONLY`):** Полное исключение AI из контура генерации публичных ответов. Диалоги сразу создаются в очереди ожидания живых специалистов (`ControlMode.PAUSED`), экономя токены и исключая риски галлюцинаций.
2. **«ИИ-агент по умолчанию» (`AI_FIRST`):** Классический сценарий первой линии AI с мягкой эскалацией на человека при затруднениях или технических сбоях.
3. **«По правилам» (`RULE_BASED`):** Интеллектуальный шлюз (Rules Engine), анализирующий расписание работы канала (`ChannelBusinessHours`), атрибуты контакта (VIP-статус, верификация), содержание сообщения (стоп-слова, претензии, регулярные выражения) и направляющий диалог соответствующему исполнителю либо профильной группе сотрудников (`EmployeeGroup`).

### 1.2. Цели QA
1. **Гарантия невовлечения AI в режиме `HUMAN_ONLY`:** Подтвердить, что ни при каких обстоятельствах не инициируются фоновые генерации ответа LLM (`request_ai_turn`), не списываются токены и не отправляются автоматические реплики клиенту.
2. **Верификация целостности очередей ожидания (Queue Integrity):** Подтвердить корректную фиксацию `waiting_since`, сохранение метки времени при повторных репликах клиента (защита от «уезда в конец очереди»), корректное ранжирование в списке диалогов и срабатывание механизма уведомлений/эскалации.
3. **Сквозная проверка логики Rules Engine:** Протестировать детерминированность вычисления условий по приоритетам (`priority ASC`), корректность работы предикатов времени с учетом часовых поясов, поиск по стоп-словам, а также безусловный fallback в очередь людей при несовпадении правил.
4. **Контроль бесшовности перехвата (Interception & Handoff):** Проверить, что отправка сообщения оператором мгновенно аннулирует вычисляемые в фоне ответы AI и блокирует последующие автоответы.
5. **Омниканальная регрессия:** Проверить идентичность работы логики для всех подключенных транспортов (Telegram, WebChat, VK, Email).

## 2. Тестовая модель и комбинаторная матрица

### 2.1. Граф состояний диалога (Conversation State Machine)

```
                       [Входящее сообщение клиента]
                                    │
                                    ▼
                     [Оценка Channel.routing_mode]
                                    │
        ┌───────────────────────────┼───────────────────────────┐
        ▼                           ▼                           ▼
  [HUMAN_ONLY]                 [RULE_BASED]                [AI_FIRST]
        │                           │                           │
        │                           ▼                           │
        │                 [Rules Engine: Priority]              │
        │                  (График, Стоп-слова, VIP)            │
        │                           │                           │
        │             ┌─────────────┴─────────────┐             │
        │             ▼                           ▼             │
        │        ROUTE_TO_HUMAN              ROUTE_TO_AI        │
        │             │                           │             │
        ▼             ▼                           │             │
  ┌─────────────────────────┐                     ▼             ▼
  │  Постановка в очередь   │              ┌─────────────────────────┐
  │ - ControlMode.PAUSED    │ ◄──(Сбой/─── │  Генерация ответа AI    │
  │ - ExpectedResponder.    │    Эскалация)│ - ControlMode.AI        │
  │   OPERATOR              │              │ - ExpectedResponder.AI  │
  │ - waiting_since = now() │              │ - request_ai_turn()     │
  └───────────┬─────────────┘              └────────────┬────────────┘
              │                                         │
              │ (Оператор берет диалог)                 │ (Оператор перехватывает диалог)
              ▼                                         ▼
  ┌─────────────────────────────────────────────────────────────────┐
  │                 Диалог у человека (ControlMode.HUMAN)           │
  │   - waiting_since = null                                        │
  │   - Фоновые генерации отменены                                  │
  └───────────────────────────────┬─────────────────────────────────┘
                                  │ (Возврат боту: "Передать ИИ")
                                  ▼
                     [Возврат в ControlMode.AI]
```

### 2.2. Матрица комбинаторного покрытия решений (Decision Table)

| Режим канала (`routing_mode`) | Наличие активного AI | Условия правил (Rules Engine) | Фактор времени / Содержание | Ожидаемый `ControlMode` | Ожидаемый `ExpectedResponder` | Вызов `request_ai_turn` | Целевая группа |
|---|---|---|---|---|---|---|---|
| `HUMAN_ONLY` | Активен | Не применимо | Любое | `PAUSED` | `OPERATOR` | **НЕТ (0 вызовов)** | Дефолтная канала |
| `HUMAN_ONLY` | Отсутствует | Не применимо | Любое | `PAUSED` | `OPERATOR` | **НЕТ** | Дефолтная канала |
| `AI_FIRST` | Активен | Не применимо | Обычный вопрос | `AI` | `CUSTOMER` (или `AI`) | **ДА** | Нет |
| `AI_FIRST` | Активен | Не применимо | «Позови человека» (эскалация) | `PAUSED` | `OPERATOR` | НЕТ (эскалация) | Дефолтная канала |
| `AI_FIRST` | Активен | Не применимо | Сбой LLM (HTTP 500 / Timeout) | `PAUSED` | `OPERATOR` | Попытка -> Fallback | Дефолтная канала |
| `AI_FIRST` | Отсутствует | Не применимо | Любое | `PAUSED` | `OPERATOR` | **НЕТ** | Дефолтная канала |
| `RULE_BASED` | Активен | Правило: Рабочие часы -> Люди | Вторник 11:00 (рабочее время) | `PAUSED` | `OPERATOR` | **НЕТ** | Согласно правилу |
| `RULE_BASED` | Активен | Правило: Нерабочие часы -> AI | Суббота 02:00 (ночь/выходной) | `AI` | `CUSTOMER` | **ДА** | Нет |
| `RULE_BASED` | Активен | Правило: Стоп-слово «претензия» | «У меня жалоба и претензия» | `PAUSED` | `OPERATOR` | **НЕТ** | Группа «Старшие» |
| `RULE_BASED` | Активен | Правило: Контакт с меткой VIP | Клиент с тегом VIP | `PAUSED` | `OPERATOR` | **НЕТ** | Группа «VIP» |
| `RULE_BASED` | Активен | Нет совпавших правил (Fallback) | Стандартное сообщение | `PAUSED` | `OPERATOR` | **НЕТ** | Общая очередь |
| `RULE_BASED` | Активен | Правило неактивно (`is_active=F`) | Условие совпадает | Срабатывает следующее правило либо Fallback | — | — | — |

## 3. Детальные сценарии тестирования (Test Cases)

### Группа 1: Режим «Только операторы» (`HUMAN_ONLY`)

#### TC-ROUT-01: Первичное обращение клиента в канал `HUMAN_ONLY`
- **Приоритет:** Blocker.
- **Предусловие:** Канал связи настроен с `routing_mode = ChannelRoutingMode.HUMAN_ONLY`. На канале подключен и включен активный `AIAgent`.
- **Шаги:**
  1. Сымитировать входящее сообщение клиента: `InboundMessage(text="Сколько стоит доставка?")`.
  2. Вызвать `ingest_inbound`.
  3. Проверить параметры созданного `Conversation`.
- **Ожидаемый результат:**
  - `conversation.control_mode == ControlMode.PAUSED`.
  - `conversation.expected_responder == ExpectedResponder.OPERATOR`.
  - `conversation.waiting_since is not None` (равно времени фиксации сообщения с точностью до миллисекунд).
  - В трансляторе очереди диалог доступен в статусе «Ожидает ответа».

#### TC-ROUT-02: Полная блокировка вызовов LLM и нулевой расход токенов
- **Приоритет:** Critical.
- **Предусловие:** Настроен mock для `chatballs.conversations.ai_turn.request_ai_turn` и внешнего шлюза провайдеров LLM.
- **Шаги:**
  1. Выполнить `ingest_inbound` 5 сообщений от разных контактов в канал `HUMAN_ONLY`.
  2. Проверить историю вызовов mock-объектов.
- **Ожидаемый результат:**
  - `request_ai_turn.assert_not_called()`.
  - Количество сетевых запросов к провайдерам LLM = 0.
  - Поле `token_usage` (если агрегируется) не увеличивается.

#### TC-ROUT-03: Уведомление операторов о новом обращении
- **Приоритет:** High.
- **Предусловие:** Канал привязан к группе операторов `EmployeeGroup("Первая линия")`, операторы онлайн (`touch(org, user)`).
- **Шаги:**
  1. Клиент присылает сообщение в канал `HUMAN_ONLY`.
  2. Проверить создание записей `Notification` в БД.
- **Ожидаемый результат:**
  - Создано уведомление `Notification` с типом `OPERATOR_REQUESTED`.
  - Адресатом выступает группа или дежурные операторы канала.

### Группа 2: Режим «ИИ-агент по умолчанию» (`AI_FIRST`)

#### TC-ROUT-04: Регрессия базового сценария AI-first
- **Приоритет:** Blocker.
- **Предусловие:** Канал с `routing_mode = ChannelRoutingMode.AI_FIRST`, агент активен.
- **Шаги:**
  1. Клиент отправляет вопрос по базе знаний.
- **Ожидаемый результат:**
  - `conversation.control_mode == ControlMode.AI`.
  - Вызван `request_ai_turn`.
  - Сгенерирован ответ модели, отправлен клиенту, диалог ожидает реплики клиента.

#### TC-ROUT-05: Эскалация по стоп-фразе оператора
- **Приоритет:** High.
- **Шаги:**
  1. Клиент пишет: «Позови человека, мне не нужен бот».
- **Ожидаемый результат:**
  - Детектируется интент эскалации.
  - Диалог переводится в `ControlMode.PAUSED`, фиксируется `waiting_since = now()`, уведомляются операторы.

#### TC-ROUT-06: Тихий Fallback при сбое LLM (Circuit Breaker / Timeout / 5xx)
- **Приоритет:** Critical.
- **Предусловие:** Внешний LLM API возвращает HTTP 500 / 429 или таймаут > 15 секунд.
- **Шаги:**
  1. Отправить входящее сообщение.
  2. Запустить обработку шага генерации AI.
- **Ожидаемый результат:**
  - Ошибка перехватывается обработчиком исключений.
  - Диалог автоматически переводится в `ControlMode.PAUSED` (`waiting_since = now()`).
  - Клиенту **НЕ отправляется** сообщение с текстом ошибки (`LLM Exception`, `Traceback`, `Service Unavailable`).
  - Для оператора сохраняется системное событие о сбое модели.

### Группа 3: Режим «По правилам» (`RULE_BASED`) и Rules Engine

#### TC-ROUT-07: Маршрутизация по расписанию (Рабочее время -> Люди)
- **Приоритет:** Blocker.
- **Предусловие:**
  - `ChannelBusinessHours`: понедельник-пятница с 09:00 до 18:00 (Europe/Moscow).
  - Правило №1 (`priority=10`): если `schedule.is_working_hours == True` -> `action_target = ROUTE_TO_HUMAN`.
  - Текущее фиктивное время: вторник, 14:00 MSK.
- **Шаги:**
  1. Подать входящее сообщение.
- **Ожидаемый результат:**
  - Правило совпало (`is_working_hours == True`).
  - Диалог создан в `ControlMode.PAUSED`, `expected_responder = ExpectedResponder.OPERATOR`. AI не вызывается.

#### TC-ROUT-08: Маршрутизация по расписанию (Нерабочее время -> AI)
- **Приоритет:** Blocker.
- **Предусловие:**
  - То же расписание. Правило №2 (`priority=20`): если `schedule.is_working_hours == False` -> `action_target = ROUTE_TO_AI`.
  - Фиктивное время: суббота, 03:00 MSK (ночь выходного дня).
- **Шаги:**
  1. Подать входящее сообщение.
- **Ожидаемый результат:**
  - Правило №1 не подошло, сработало Правило №2.
  - Диалог передан AI-агенту (`ControlMode.AI`), инициирован `request_ai_turn`.

#### TC-ROUT-09: Учет часовых поясов и праздничных дней
- **Приоритет:** High.
- **Предусловие:**
  - Таймзона канала `Asia/Vladivostok` (UTC+10).
  - Список `holidays`: `["2026-05-01", "2026-01-01"]`.
- **Шаги:**
  1. Проверить вычисление в 00:30 UTC 1 мая 2026 года (10:30 по Владивостоку).
- **Ожидаемый результат:**
  - Дата распознается как праздник (`holidays`), `is_working_hours == False`.

#### TC-ROUT-10: Фильтрация по стоп-словам (Претензии и жалобы)
- **Приоритет:** Critical.
- **Предусловие:**
  - Правило (`priority=5`): `field="message.text_contains", op="contains_any", value=["жалоба", "претензия", "суд", "возврат"]` -> `ROUTE_TO_HUMAN`, `target_group="Старшие специалисты"`.
- **Шаги:**
  1. Клиент пишет: «Я намерен подать претензию и обратиться в суд!».
- **Ожидаемый результат:**
  - Правило с наивысшим приоритетом срабатывает независимо от расписания.
  - Диалог направляется напрямую операторам, поле `conversation.group` установлено на группу «Старшие специалисты».

#### TC-ROUT-11: Сегментация по VIP-клиентам (`contact.labels`)
- **Приоритет:** High.
- **Предусловие:**
  - Правило: контакт имеет метку `VIP` -> `ROUTE_TO_HUMAN`, группа «VIP-поддержка».
- **Шаги:**
  1. Сообщение от клиента с `contact.labels = ["VIP", "Enterprise"]`.
- **Ожидаемый результат:**
  - Диалог сразу маршрутизируется операторам группы «VIP-поддержка».

#### TC-ROUT-12: Соблюдение порядка приоритетов правил (First-Match)
- **Приоритет:** High.
- **Предусловие:**
  - Правило A (`priority=10`): «содержит слово 'акция'» -> `ROUTE_TO_AI`.
  - Правило B (`priority=20`): «VIP-клиент» -> `ROUTE_TO_HUMAN`.
- **Шаги:**
  1. VIP-клиент пишет сообщение: «Расскажите про условия новой акции».
- **Ожидаемый результат:**
  - Срабатывает Правило A (`priority=10 < 20`), диалог идет боту.
  - Инверсия: при смене приоритетов (Правило B = 5, Правило A = 10) диалог того же клиента обязан пойти человеку.

#### TC-ROUT-13: Гарантированный Fallback по умолчанию
- **Приоритет:** Blocker.
- **Предусловие:**
  - Канал в режиме `RULE_BASED`. В списке правил ни одно условие не подошло.
- **Шаги:**
  1. Клиент пишет произвольный текст «123 abc».
- **Ожидаемый результат:**
  - Rules Engine исчерпывает список правил без совпадений.
  - Срабатывает системный дефолт: `RouteDecision(target=ROUTE_TO_HUMAN)`.
  - Диалог помещается в очередь операторов. Обращение ни при каких условиях не теряется.

### Группа 4: Сквозное тестирование очередей ожидания (Queue Integrity)

#### TC-ROUT-14: Сохранение метки `waiting_since` при повторных обращениях клиента
- **Приоритет:** Blocker.
- **Предусловие:** Диалог находится в очереди (`ControlMode.PAUSED`, `waiting_since = T0`).
- **Шаги:**
  1. Спустя 10 минут клиент пишет: «Вы ответите или нет?».
- **Ожидаемый результат:**
  - Поле `conversation.waiting_since` остается строго равным `T0` (не перезаписывается текущим временем).
  - Поле `conversation.last_message_at` обновляется текущим временем.
  - Клиент сохраняет приоритетное место в начале очереди операторов.

#### TC-ROUT-15: Сортировка очереди в селекторах (`order_conversations`)
- **Приоритет:** High.
- **Предусловие:**
  - Диалог А ждет с 10:00.
  - Диалог Б ждет с 10:30.
  - В 10:40 клиент Диалога А отправляет повторное сообщение.
- **Шаги:**
  1. Выполнить `order_conversations(qs, "waiting")`.
- **Ожидаемый результат:**
  - Диалог А строго предшествует Диалогу Б в списке ожидания.

#### TC-ROUT-16: Мгновенный перехват оператором (Interception)
- **Приоритет:** Critical.
- **Предусловие:** Диалог обслуживается AI (`ControlMode.AI`), запущена генерация ответа.
- **Шаги:**
  1. Оператор вводит текст ответа и нажимает «Отправить».
- **Ожидаемый результат:**
  - Синхронно в транзакции отправки:
    * `conversation.control_mode` становится `ControlMode.HUMAN`.
    * `conversation.waiting_since` сбрасывается в `None`.
  - Любой пришедший результат отложенной генерации AI аннулируется и не отправляется клиенту.
  - Последующие входящие реплики клиента не будят AI.

#### TC-ROUT-17: Передача диалога обратно боту («Вернуть ИИ-агенту»)
- **Приоритет:** Medium.
- **Предусловие:** Диалог ведет оператор (`ControlMode.HUMAN`).
- **Шаги:**
  1. Оператор вызывает действие «Передать ИИ-агенту».
  2. Клиент отправляет следующее сообщение.
- **Ожидаемый результат:**
  - `conversation.control_mode` переходит в `ControlMode.AI`.
  - Входящее сообщение клиента обрабатывается ботом по стандартному сценарию.

### Группа 5: Граничные и негативные случаи (Edge Cases & Resilience)

#### TC-ROUT-18: Удаление целевой группы (`SET_NULL`)
- **Приоритет:** Medium.
- **Предусловие:** В правиле указана `target_group = Group #42`.
- **Шаги:**
  1. Удалить `EmployeeGroup #42` из системы.
  2. Подать сообщение, подпадающее под это правило.
- **Ожидаемый результат:**
  - В правиле `target_group` становится `None` (благодаря `SET_NULL`).
  - Диалог направляется в общий пул операторов канала без падения с ошибкой 500.

#### TC-ROUT-19: Некорректный или пустой JSON условий правила
- **Приоритет:** High.
- **Предусловие:** В поле `conditions` правила передан некорректный синтаксис (например, отсутствуют обязательные поля `field`/`op`).
- **Шаги:**
  1. Подать сообщение в канал.
- **Ожидаемый результат:**
  - Движок правил перехватывает ошибку валидации предиката.
  - В журнал аудита/логов пишется предупреждение.
  - Диалог мягко деградирует в очередь операторов (`ROUTE_TO_HUMAN`).

#### TC-ROUT-20: Строгая изоляция тенантов (Multi-Tenancy RLS)
- **Приоритет:** Blocker.
- **Шаги:**
  1. Создать правила маршрутизации в Организации 1.
  2. Отправить сообщение в канал Организации 2.
- **Ожидаемый результат:**
  - Ни одно правило Организации 1 не учитывается при маршрутизации канала Организации 2 (`organization_id` фильтруется на уровне SQL/ORM).

from unittest import mock
from django.test import TestCase
from django.utils import timezone

from chatballs.conversations.models import ControlMode, ExpectedResponder, Conversation

from chatballs.integrations.models import Integration, IntegrationKind, IntegrationProvider

class FlexibleRoutingIngestTests(TestCase):

## 5. Критерии приемки (DoD) и право вето QA (Release Gating)

### 5.1. Definition of Done для выпуска функционала
1. **100% покрытие ключевых сценариев:** Все тесты категорий Blocker и Critical (TC-ROUT-01 — TC-ROUT-17) реализованы и успешно проходят в CI.
2. **Нулевая утечка токенов в `HUMAN_ONLY`:** Ни один вызов Celery задачи AI-агента не генерируется при активном режиме операторов.
3. **Отсутствие технических терминов в UI:** В интерфейсе настроек каналов и конструкторе правил соблюден регламент UX Writing (русский язык, отсутствие терминов вроде `ROUTE_TO_AI`, `ControlMode.PAUSED`).
4. **Сохранение SLA очереди:** В диалогах при любых условиях сохраняется первичный `waiting_since` до момента ответа или перехвата оператором.

### 5.2. Условия применения права вето (Release Gating)
Ведущий инженер по контролю качества **немедленно блокирует передачу задачи в релиз** при наличии:
- Хотя бы одного случая непреднамеренного ответа AI в канале с режимом `HUMAN_ONLY`.
- Сброса времени `waiting_since` при повторном сообщении клиента, приводящего к потере позиции в очереди.
- Падения сервера с кодом 500 при несовпадении правил или пустом расписании.
- Утечки служебных сообщений или стектрейсов ошибок LLM клиенту в мессенджер.
