## 1. Введение и цели тестирования

### 1.1. Контекст инициативы
В рамках стратегической модернизации интерфейса платформы Chatballs выполняется полный перевод кодовой базы фронтенда с библиотеки **Ant Design** (`antd`, `@ant-design/icons`) на дизайн-систему **Consta UI** (`@consta/uikit`, `@consta/icons`, `@consta/header` и сопутствующие пакеты экосистемы).

Подлежащие миграции пакеты и приложения:
- `@chatballs/ui` (`packages/ui`) — базовая дизайн-система и переиспользуемые UI-компоненты.
- `@chatballs/internal-ui` (`apps/internal-ui`) — рабочее место оператора, контакт-центр, база знаний, порталы, аналитика, настройки.
- `@chatballs/web-chat` (`apps/web-chat`) — клиентский встраиваемый веб-виджет чата, звонков и обратной связи.

### 1.2. Цели QA
1. **Функциональная эквивалентность:** Гарантировать сохранение всей полноты бизнес-логики и сценариев взаимодействия пользователей без деградации функциональности.
2. **Визуальная целостность и отсутствие артефактов:** Исключить визуальные баги, некорректные стили, наложения слоёв (z-index), поломку сетки, «съехавшие» шрифты и отступы.
3. **Чистота сборки и зависимостей:** Подтвердить стопроцентное удаление артефактов `antd` и `@ant-design/icons` из `package.json`, бандлов и рендеринга DOM.
4. **Стабильность кросс-браузерности и тем:** Проверить корректность рендеринга и контрастности в светлой (`presetChatballsDefault`) и тёмной (`presetChatballsDark`) темах, а также в адаптивных режимах (Desktop, Tablet, Mobile).

## 2. Область тестирования (Scope)

### 2.1. Входит в область тестирования (In Scope)
1. **Ядро дизайн-системы (`@chatballs/ui`):**
   - Провайдер темы `<Theme preset={...}>` (светлая/тёмная темы, переключение «на лету»).
   - Шрифтовой стек, масштабирование типографики `Text`, глобальные CSS-переменные токенов.
   - Компоненты аудио/видеовызовов (`CallStage`, оверлеи).
2. **Рабочее место оператора (`apps/internal-ui`):**
   - Авторизация, сессия, переключение языков (RU/EN).
   - Лейаут: глобальный `Sidebar`, `Header`, мобильная шапка `ChatMobileHeader`.
   - Раздел «Диалоги» (3-колоночный сплит): список диалогов, фильтры, карточка переписки, композитор (ввод сообщений, вложения, эмодзи-пикер, шаблоны ответов), контекстная панель клиента.
   - Аудиозвонки и видеозвонки оператора (модальные оверлеи).
   - База знаний и AI-агенты: модалки привязки агентов, создание категорий, карточки статей.
   - Настройки и интеграции: модальные окна интеграций, шторка уведомлений (`Sidebar`/Drawer), всплывающие тосты (`SnackBar`).
   - Разделы сотрудников, продаж и порталов самообслуживания.
3. **Клиентский виджет (`apps/web-chat`):**
   - Плавающая кнопка вызова (FAB), раскрытие/сворачивание виджета.
   - Список сообщений, отправка текста, прикрепление файлов, индикаторы статуса отправки/прочтения.
   - Экран аудио- и видеозвонка клиента.
   - Полноэкранный и мобильный режимы.
4. **Нефункциональные характеристики:**
   - Производительность рендеринга (FPS при скролле длинных диалогов, размер бандла).
   - Доступность (a11y): навигация с клавиатуры (`Tab`, `Esc`, `Enter`), поддержка `focus-visible`, атрибуты ARIA.

### 2.2. Не входит в область тестирования (Out of Scope)
- Бэкенд API бизнес-логики (проверяется только контрактное взаимодействие и обработка ошибок фронтендом).
- Внешние провайдеры авторизации и сторонние API (Telegram, VK, email-шлюзы) — тестируются на уровне моков или валидации интерфейса форм.

## 3. Стратегия и методология тестирования

Тестирование организуется в форме пирамиды контроля качества:

```
          / \
         / E2E \       <- Playwright (сквозные сценарии, скриншотный регресс)
        /-------\
       /  Integ  \     <- Vitest + RTL (компоненты форм, модалки, контексты)
      /-----------\
     /    Unit     \   <- Vitest (хелперы, мапперы данных, селекторы токенов)
    /---------------\
   / Static Analysis \ <- ESLint, TSC typecheck, AST/Grep-валидация зависимостей
  /-------------------\
```

### 3.1. Уровни тестирования

| Уровень | Инструменты | Ответственный | Критерий прохождения |
|---|---|---|---|
| **Статический анализ** | TypeScript (`tsc --noEmit`), ESLint, `grep`/depcheck | CI / Frontend Dev | 0 ошибок типизации, 0 импортов `antd` |
| **Модульное (Unit)** | Vitest | Frontend Dev | 100% прохождение существующих и новых тестов |
| **Компонентное/Интеграционное** | Vitest + React Testing Library | Frontend Dev / QA | Корректный рендеринг состояний компонентов Consta |
| **Сквозное (E2E)** | Playwright (`tests/e2e/`) | QA Engineer | Зелёный прогон сьютов `internal-ui.spec.ts`, `apps.spec.ts` |
| **Визуально-регрессионное** | Playwright Visual Comparisons (`toHaveScreenshot`) | QA Engineer | Отсутствие визуальных дельта-расхождений |
| **Ручное исследовательское** | Браузеры (Chrome, Firefox, Safari, Mobile Emulation) | Lead QA | Подтверждение чек-листа интерактивных состояний |

## 5. Специфические тестовые сценарии (End-to-End Test Cases)

### Сценарий 1: Обработка обращения оператором (Internal UI)
- **Предусловие:** Оператор авторизован в системе, открыт раздел диалогов.
- **Шаги:**
  1. Выбрать диалог из списка переписки.
  2. Проверить отображение активного состояния выбранного диалога (акцентный левый бордер, фон).
  3. В поле ввода сообщения (`TextField`) ввести текст, добавить эмодзи через пикер (`Popover`), прикрепить файл.
  4. Нажать кнопку отправки (`Button view="primary"`).
  5. Открыть меню действий с диалогом (`ContextMenu` / `ActionMenu`), выбрать «Назначить на меня».
- **Ожидаемый результат:** Сообщение мгновенно отображается в ленте; меню открывается строго под кнопкой-триггером; состояние диалога меняется; консоль браузера чиста от варнингов и ошибок `undefined/antd`.

### Сценарий 2: Переключение тем оформления («На лету»)
- **Предусловие:** Пользователь находится на любой странице системы.
- **Шаги:**
  1. Открыть пользовательское меню в `Sidebar`.
  2. Переключить тумблер/пункт смены темы (Светлая -> Тёмная).
  3. Проверить визуальный вид всех видимых элементов.
  4. Перезагрузить страницу (F5).
- **Ожидаемый результат:** Все фоны (`--color-bg-default`), тексты (`--color-typo-primary`) и границы (`--color-bg-border`) мгновенно инвертируются согласно пресету `presetChatballsDark`. Нет элементов с инвертированным или нечитаемым текстом (чёрный текст на тёмном фоне). После перезагрузки сохранённое состояние темы сохраняется.

### Сценарий 3: Клиентский веб-чат и мобильная адаптивность
- **Предусловие:** Веб-виджет размещён на тестовой странице.
- **Шаги:**
  1. Кликнуть на плавающую кнопку вызова виджета (FAB).
  2. Ввести обращение, отправить сообщение.
  3. Запустить аудиозвонок.
  4. Изменить размер viewport до 375x667 (эмуляция мобильного экрана).
- **Ожидаемый результат:** Окно чата плавно открывается с тенью Level 3; на мобильном экране виджет разворачивается на 100% ширины и высоты экрана; элементы управления звонком не обрезаются и удобны для нажатия пальцем (touch target >= 44x44px).

## 6. Критерии приемки (Acceptance Criteria)

### 6.1. Критерии отсутствия визуальных багов (Zero Visual Bugs)
1. **Отсутствие артефактов верстки (Pixel-Perfect Alignment):**
   - Все отступы соответствуют 4px-сетке (`space-xs`, `space-s`, `space-m`, `space-l`).
   - Отсутствуют переполнения контейнеров (`overflow clipping`), горизонтальный скролл на десктопных страницах и наложения текста.
2. **Иерархия слоев (Z-Index Hierarchy):**
   - Выпадающие списки (`Select`), контекстные меню (`ContextMenu`), модальные окна (`Modal`), шторки (`Sidebar`) и системные тосты (`SnackBar`) имеют строго выверенный z-index:
     `Content (0) < Sticky Headers/Sidebars (10) < Drawers/Sidebars (100) < Modals (1000) < Dropdowns/Popovers (2000) < Toasts/SnackBar (3000)`.
   - Исключены ситуации перекрытия модальных окон фоновым контентом или "залипания" оверлеев.
3. **Контрастность и читаемость (WCAG 2.1 AA):**
   - Коэффициент контрастности текста относительно фона составляет не менее **4.5:1** для обычного текста и не менее **3:1** для крупных заголовков как в светлой, так и в тёмной теме.
4. **Скругления и бордеры:**
   - Единый радиус скругления элементов `8px` (`radius-m`), для компактных полей ввода — `6px` (`radius-s`). Отсутствуют элементы с дефолтными прямоугольными рамками браузера.
5. **Состояния интерактивности:**
   - Ни один интерактивный элемент не остается без визуального отклика на `hover`, `active` и `focus-visible`.

### 6.2. Критерии отсутствия логических багов (Zero Functional/Logical Bugs)
1. **Сохранение бизнес-потоков:**
   - Ни одно действие пользователя (отправка сообщения, фильтрация, создание статьи БЗ, изменение прав сотрудника, перевод звонка) не приводит к зависанию, потере введенных данных или сбою стейта.
2. **Обработка краевых и граничных случаев (Edge Cases):**
   - Экстремально длинные строки (до 500 символов без пробелов) корректно переносятся (`word-break: break-word`) или обрезаются троеточием (`text-overflow: ellipsis`), не ломая контейнер.
   - Пустые списки отображают понятный `Empty state` с поясняющим текстом и кнопкой действия.
   - Медленная сеть: индикаторы `Loader` и состояние кнопки `loading={true}` блокируют повторные клики и предотвращают двойную отправку запросов (double-submit).
   - Ошибки сети/валидации: форма подсвечивает проблемные поля (`status="alert"`), а система выводит уведомление через `SnackBar`.
3. **Фокус и клавиатурная навигация:**
   - При открытии модального окна фокус перемещается внутрь диалога (Focus Trap).
   - Нажатие клавиши `Esc` закрывает верхний открытый слой (меню -> модалку -> шторку).
   - Нажатие `Tab` осуществляет циклическую навигацию по интерактивным элементам диалога.

### 6.3. Критерии чистоты кодовой базы и зависимостей (Technical Gate)
1. **Полное исключение Ant Design:**
   - В бандлах и кодовой базе приложений отсутствуют модули `antd`, `@ant-design/icons`, `@ant-design/cssinjs`.
   - В итоговом DOM-дереве страниц отсутствуют классы с префиксом `ant-` (например, `ant-btn`, `ant-dropdown`, `ant-modal` и т.д.).
2. **Прохождение автоматических проверок:**
   - Команда `npm run typecheck` завершается с кодом `0` (отсутствие TS-ошибок).
   - Команда `npm run test` (Vitest) завершается со 100% успехом.
   - Команда `npx playwright test` (E2E) завершается со 100% успехом на поддерживаемом пуле браузеров.

## 8. Процедура блокировки релиза (Release Gating & Right to Veto)

В соответствии с полномочиями **Ведущего инженера по контролю качества (Lead QA Engineer)**:
- При обнаружении хотя бы одного дефекта уровня **Critical** (блокер основного сценария, краш приложения, невозможность отправить сообщение или ответить на звонок, остаточные следы antd в рантайме) накладывается **безусловное вето на релиз**.
- Релиз блокируется переводом соответствующей задачи разработки в статус `blocked` или возвратом `changes_requested` с приложением подробного протокола дефектов (шаги воспроизведения, скриншоты расхождений, логи консоли).
- Снятие вето возможно исключительно после устранения дефектов и успешного повторного прохождения регрессионного сьюта под контролем Lead QA.
