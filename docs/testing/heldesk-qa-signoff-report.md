## 3. Детальные результаты по направлениям

### 3.1. Тестирование контрактов API и модели данных
- **Эндпоинты `/api/v1/organizations/{org_id}/tickets/*`:**
  - Валидация создания заявки (`POST /`): генерация уникального номера с префиксом (`TKT-000001`), установка статуса `NEW`, начальной версии `version = 1`. Обязательность темы (`subject`), валидация допустимых категорий и приоритетов.
  - Детальный просмотр (`GET /{id}/`): выдача полной информации о заявителе, исполнителе, группе, временных метках и связях.
  - Частичное обновление (`PATCH /{id}/`): модификация приоритета, темы, описания и назначения. Запрет изменения `organization_id` и `id`.
  - Машина состояний (`POST /{id}/transitions/`): допустимые переходы (`NEW -> IN_PROGRESS -> RESOLVED -> CLOSED`) отрабатывают корректно с фиксацией `resolved_at` и `closed_at`.
  - Недопустимые переходы (например, `NEW -> CLOSED` минуя решение, либо перевод из терминальных состояний `CLOSED`, `CANCELLED`, `DUPLICATE`) блокируются с кодом `400 Bad Request` (`invalid_transition`).
  - Обязательность причины для статусов `RESOLVED`, `CLOSED`, `CANCELLED`, `DUPLICATE` подтверждена тестами.
- **Оптимистическая блокировка (Optimistic Concurrency Control):**
  - При несовпадении переданного `expected_version` с текущей версией записи в БД сервер немедленно возвращает `409 Conflict` с указанием актуальной версии (`current_version`). Конкурентная перезапись изменений исключена.

### 3.2. Тестирование мультиарендности, RLS и ролевого доступа (RBAC)
- **Межорганизационная изоляция (Multi-tenancy):**
  - Запросы списков заявок (`GET /api/v1/tickets/`) строго фильтруются текущим тенантом: заявки организации `org2` не отображаются пользователям `org1`.
  - Прямые запросы по ID чужой заявки (`GET /api/v1/tickets/{org2_id}/`, `PATCH`, `POST transitions/`, `GET notes/`, `POST comments/`) отклоняются с кодом `404 Not Found`, гарантируя защиту от сканирования IDOR.
  - Попытка связать заявку организации 1 с контактом или диалогом организации 2 блокируется на уровне API и DB Guards (`t01_enforce_tenant_pair`).
  - Неавторизованные запросы к защищенным путям организаций блокируются с кодом `404/401`.
- **Ролевая модель:**
  - `OWNER` и `ADMIN`: полный доступ к просмотру реестра, созданию, обновлению, переводу статусов, внутренним заметкам и комментариям.
  - `EMPLOYEE`: доступ к работе с заявками в рамках полномочий оператора поддержки (`tickets.view`, `tickets.manage`).

### 3.3. Тестирование конвейера уведомлений и подавления
- **Outbox и доставка:**
  - При создании заявки формируются запись `TicketDelivery` со статусом `PENDING` и Outbox-события `tickets.delivery_dispatched`.
  - Фоновый обработчик воркера гарантирует доставку уведомления в правильный канал получателя (Email/Web-чат/мессенджер) с обновлением статуса на `SENT`.
  - Дедупликация: повторная диспетчеризация того же события с тем же `destination_hash` не создает дублирующих отправок.
  - Обработка сбоев: при временной ошибке транспорта сохраняется счетчик попыток `attempt_count` и выставляется `next_attempt_at`.
- **Сценарий подавления («Не уведомлять клиента»):**
  - Подтверждено: передача `customer_notice = "SUPPRESS"` при добавлении комментария или смене статуса формирует запись доставки со статусом `SUPPRESSED`.
  - Реальная внешняя отправка клиенту полностью блокируется, при этом в журнале аудита (`TicketEvent`) и таблице доставок сохраняется факт изменения и причина подавления (`suppression_reason`).
  - Подавление клиентских уведомлений не влияет на доставку внутренних уведомлений сотрудникам (`staff_notifications`).

### 3.4. Интеграционное и сквозное E2E тестирование
- **Интеграция с диалогами чата:**
  - Создание заявки из активного `Conversation` через эндпоинт `/api/v1/conversations/{id}/ticket/`: автоматически проставляются ссылки `TicketConversationLink` и `TicketContactLink` со связью с заявителем (`requester`).
  - Проверена устойчивость к удалению диалога: при физическом удалении `Conversation` срабатывает `models.SET_NULL`, заявка сохраняется в базе и остаётся доступной операторам в неизменном виде со сброшенным `origin_conversation_id = null`.
- **Клиентский интерфейс (Consta UI):**
  - `TicketsPage`: таблица заявок корректно отображает бейджи статусов, уровни приоритетов, контакты и даты.
  - `TicketDetailPage`: вкладки комментариев, внутренних заметок и хронологии аудита изолированы и функционируют без сбоев.
  - `TicketStatusActions`: кнопки разрешенных переходов формируются строго по матрице допустимых состояний, открывают модальное окно запроса причины для терминальных статусов и обрабатывают `409 Conflict`.
  - `CreateTicketModal`: модальное окно создания заявки валидирует обязательные поля и отправляет данные в API.

### 3.5. Регрессионное тестирование базовой платформы
- **Базовые диалоги и маршрутизация:**
  - Запущены регрессионные наборы тестов `chatballs/channels/test_routing_api.py`, `chatballs/channels/test_routing_rules.py`, `chatballs/conversations/test_lifecycle.py`, `chatballs/conversations/test_conversation_delete.py`, `chatballs/conversations/test_flexible_routing_ingest.py`, `chatballs/conversations/test_flexible_routing_transitions.py`.
  - Все 69 регрессионных тестов завершились со статусом `PASS`.
  - Внедрение сущностей `Ticket` не затронуло работу существующих очередей, алгоритмов маршрутизации каналов, правил Rules Engine и механизма передачи диалогов искусственному интеллекту (AI handoff).
